# 关键判断、证据和玩家反馈

手册（`data/matchups/*.md`、`data/archetypes/*.yaml`）里能被一局对局证明对错的判断，比如"镜像选后攻"，
在这里登记，带一个信心。之后每次复盘录像或对局记录、每条玩家反馈，都记下这个判断成立没有，信心随之更新。
手册里的写法是 `（信心 70%，akd-mir-01）`，数字由 `python -m ptcg.judgments sync` 按这里的记录重算。

卡牌文字和伤害计算能直接核对的不算判断：核对后当作事实写进手册。

## 文件

| 路径 | 内容 |
|---|---|
| `<卡组>.yaml` | 这套卡组的判断：`id`、`vs`（对手卡组）、`text`、`confidence`（写下时的信心，0.5-0.99）、`weight`（这个信心值几局，默认 4）、`basis`（依据）、`window`（最近一次复查时的卡池窗口）、`depends_on`（依赖的卡）、`where`（带标记的手册文件）、可选 `alternative_to`（它是哪个判断的备选路线） |
| `sources/<日期>_<log/video/feedback>_<名字>.yaml` | 一次复盘或一条反馈：`observations` 逐条记判断成立没有，`claims` 记它提出、还没有登记成判断的新东西 |
| `review-checklist.md` | 每次复盘都要过一遍的清单，包括反馈指出过的复盘盲点 |
| `feedback-template.md` | 发给玩家的英文反馈模板（可选） |

## 信心怎么算

当前信心 = (写下时的信心 × weight + 成立的次数) / (weight + 记录次数)。对局记录和录像每局算 1 次；
玩家反馈的同意 / 不同意算 0.5 次。所以一条反馈只会挪动信心，不会推翻结论；几局对局结果才会。
信心跌到 50% 以下时 `check` 会提醒：要么改写手册里那句话，要么把反过来的判断登记成新判断。

`calibration` 检查信心标得准不准：标 70% 的判断，事后是不是大约七成成立。每个结果按它发生之前的信心计。

## 一条玩家反馈怎么处理

1. 原文一字不改存进项目共享文件夹 `feedback/raw/<日期>_<代号>_<针对的复盘>.md`。仓库是公开的，原文和玩家真名不进仓库。
2. 拆成论点，写 `sources/<日期>_feedback_<代号>.yaml`：`reviewer` 只写代号，`reviewer_context` 写他打什么、什么水平。
   - 针对已登记判断的，记成 `observations`，`result` 是 `agree` 或 `disagree`。
   - 新东西记成 `claims`，`type` 是 纠错 / 新打法 / 全局观 / 备选路线 / 玩家观点 / 复盘盲点 之一。
3. 处理 claims：
   - 能用卡牌文字、伤害计算核对的，直接核对，`status: 已核对`，对的改进手册，错的在 `note` 写为什么错。
   - 偏好类，`status: 观点`。另一个玩家独立提出同样的看法时，改成 `待验证`。
   - 新打法、全局观、备选路线，`status: 待验证`，`check` 写要找什么证据。要进手册的，登记成判断（信心不超过 0.6，
     weight 2），手册里标"（玩家反馈）"，claim 改成 `已转正` 并填 `promoted_to`。
   - 备选路线登记时填 `alternative_to`，手册里和主线并列，写清什么条件下它更好。两条路线的信心各自更新，
     备选超过主线时对调位置，旧主线留作备选，不删。
   - 复盘盲点（"你只算了奖赏卡，没看对手手牌资源"）加进 `review-checklist.md`。
4. `python -m ptcg.judgments sync` 更新手册里的数字，`check` 通过后提交。改了手册的，同步刷新项目共享文件夹
   `deck-selection/matchups/` 里的副本。

## 每次复盘时

复盘录像或对局记录前，先跑 `python -m ptcg.judgments pending <卡组> <对手>`，列出这个对局登记过的判断和待验证的论点，
复盘时逐条看这局有没有碰到。碰到的写进这次复盘的 `sources/` 文件：成立 `held`，不成立 `failed`，局面没出现 `n/a`。
只记登记之后的对局，写判断时用作依据的那几局不再重复计。

## 跟着格式变

每周的 `collect` 工作流跑完后执行 `python -m ptcg.judgments stale`，有结果就开一个 issue（不让工作流失败）。
算"需要复查"的情况：依赖的卡已不在 Standard；或者进入了新的卡池窗口，而这套卡组或对手卡组带某张依赖卡的比例
变了 25 个百分点以上，或者对手已不在主流卡组里。复查后把 `window` 改成当前窗口；不再成立的判断写一条 `failed`
观察并改写手册，不删除，留作以后类似牌型的参考。
